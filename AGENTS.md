# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax

# Pokemon Center — Project Ruleset

_The authoritative reasoning lives in [docs/master-plan.md](docs/master-plan.md); this is the always-load summary. Per-domain plans: [pokedex-product-plan.md](docs/pokedex-product-plan.md), [school-plan.md](docs/school-plan.md), [arena-plan.md](docs/arena-plan.md)._

## Core vision

Pokemon Center is the data + services hub of the pokemon-verse: **one canonical Pokemon database, one read-only GraphQL API**, consumed by every sibling project and by three interconnected domains:

- **Pokedex** — interconnected knowledge base (Pokemon, moves, items, abilities, types) with advanced search/filtering and bi-directional linking. MVP scope: **Generation 1**.
- **School** — interactive training ground: lessons + simulations generated from the mechanics data.
- **Arena** — mechanically accurate turn-based battle engine, engine-first.

Strategic bet: every domain and sibling project is a projection of the same relational dataset. Get the dataset and its API right once; everything downstream gets cheaper.

## Non-negotiable stack

- Frontend **Angular 22** · Monorepo **Nx 23** · Backend **NestJS 11** · Package manager **pnpm**
- API: **GraphQL**, code-first via `@nestjs/apollo`, **read-only** for reference data (Query types only, no mutations)
- DB: **PostgreSQL 17** via Docker Compose · ORM: **Prisma 7** (`schema.prisma` → client → `prisma-nestjs-graphql` entities, regenerated on install)
- Search: **Postgres FTS** (`pg_trgm` + generated `tsvector`) — Elasticsearch is **mothballed, not in the MVP**
- State: **`@ngrx/signals` is a core dependency (owner's decree)** — `signalStore` for any shared/lifecycle state; bare `signal`/`computed`/`linkedSignal` for local component state
- Frontend data layer: **GraphQL Codegen** typed documents + Angular **`httpResource`** (no Apollo Angular unless a normalized cache or subscriptions are actually needed)
- Tests: **Jest 30**

## Conventions

- **Canonical IDs**: `pokemon:25`, `move:63` — plus a human slug (`pikachu`) for URLs/lookups. Enforced at the resolver layer; never leak DB integer PKs into API identity.
- **Generated code** (`prisma-client/`, `entities/`) is committed, eslint-ignored, and never hand-edited — it is regenerated by `postinstall`.
- **Git**: all work on descriptively-named feature branches, never directly on `main`; frequent conventional commits; PRs into `main` summarizing the work.
